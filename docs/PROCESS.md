# Unified Development Process v1.0

- **Status:** Owner-approved contract
- **Canonical source:** This document
- **Approved scope:** [danielbyon/development-process Issue #1](https://github.com/danielbyon/development-process/issues/1)

This policy is the complete v1.0 process. Project instructions and future Skills adapt it; they do not replace or override it.

The final amendments are incorporated in the policy: every task uses an isolated worktree and dedicated branch (§4); one non-waivable predicate covers confirmed in-scope or candidate-introduced/materially-worsened P0/P1 defects (§6); and new tasks pin a verified immutable release and continuing tasks retain their recorded pins (§12).

## 1. Roles and authority

- ChatGPT owns requirements investigation, planning, Codex plan approval or revision, independent direct source and test inspection through MCP or GitHub, review adjudication, technical readiness, and cleanup for ChatGPT-implemented changes. **No ChatGPT source access means no approval.**
- Codex owns implementation in an isolated worktree, delegation setup, local validation, local Cubic review coordination, draft PR publication, authorized corrections, and cleanup for Codex-implemented tasks when it is eligible.
- Every change, including trivial non-code changes, requires independent review from a separate non-authoring review execution. Local Cubic is preferred; a separate Codex subagent is the fallback. Cubic CI review is supplementary when quota permits.
- The owner approves product and material architectural trade-offs, substantive gate exceptions, substantive policy revisions, and merging. No human manual code review is assumed.

## 2. Scope, planning, risk

- Substantive tasks use a GitHub issue with proportionate acceptance criteria, relevant specifications, constraints, and exclusions. Serial implementation per repository is the default; explicitly independent parallel work is supported.
- Normal or routine work has clear requirements and existing patterns, with no unresolved material design decisions. Elevated-risk work involves consequential data, privacy, authorization, persistence, recovery, destructive, or hardware behavior; specify failure modes and targeted verification.
- Straightforward changes may omit a separate Codex plan. Every plan Codex produces requires ChatGPT approval before implementation, and material plan revisions require another review. Read-only Codex planning and ChatGPT plan approval may precede worktree bootstrap; isolated execution remains mandatory under §4.
- Preserve decisions with their rationale, rejected alternatives, invariants, and failure modes. ChatGPT approves routine technical choices within the accepted design; the owner decides material scope, product, architecture, and security trade-offs.

## 3. Engineering choices

- Before implementing a substantial custom subsystem, investigate native capabilities and maintained libraries or frameworks. Assess functionality, license, maintenance, security, integration, and complexity.
- Avoid adversarial overengineering outside the approved threat model. Escalate meaningful trade-offs to the owner.

### Task-independent implementation naming

- Apply this rule to types, functions, methods, variables, and constants; test and fixture names; scripts and first-party generators; maintained technical documentation and source comments; logging, diagnostic, and configuration strings; and implementation-owned file and directory names. Use behavior, domain, or stable-technology names and strings instead of temporary task identity. The rule applies inside task-named worktrees. Plan approval does not grandfather a task-derived name.
- Distinguish task-history references from stable domain and protocol identifiers. Keep task IDs in records whose purpose is to track the task, including issues, plans, ADRs and governance records, evidence, GitHub records, branch and worktree labels, and Git metadata. Preserve protocol versions and numeric identifiers when they carry stable domain meaning, even when they resemble task labels.
- Review the actual names changed by the task. Remove a task-only reference from an implementation comment when it no longer explains the code, and retain verified engineering rationale such as a constraint or failure mode. Do not replace a useful explanation with an unexplained name change.
- Preserve compatibility-sensitive names and strings, including public APIs, persisted keys, serialized fields and data, wire formats, reflection-visible names, and dynamically looked-up strings. A configuration key, log or diagnostic event, file name, or comment consumed by another component may also be compatibility-sensitive; verify its consumers before changing it. These surfaces remain in scope for review, but do not rename a confirmed compatibility-sensitive instance solely to remove task identity; treat it as Tier 2 and require separate owner-approved migration scope before changing it.
- This rule does not authorize a control-flow, external-behavior, or compatibility change. A naming change must fit the accepted task scope.
- **Tier 1:** A behavior-preserving coordinated rename of an internal name is allowed when verified reference and compatibility evidence supports it. Check and update affected callers, tests, generated output, and documentation, then validate the change.
- **Tier 2:** A compatibility-sensitive rename requires a separate owner-approved migration plan and scope. This policy does not authorize one.
- When a first-party generator owns a name, change the generator and regenerate its output. Do not hand-edit generated output or vendored dependencies.
- Fix confirmed naming violations introduced or materially worsened by the candidate, and violations within its accepted slice, before merge. Separately tracked pre-existing violations do not by themselves block an otherwise complete slice; keep the repository-wide cleanup obligation open until its closure criteria are met. This policy establishes task-independent naming and review practice; it does not authorize a repository-wide rename or compatibility migration.
- Enforce this rule through author self-review and the existing independent-review process. Do not introduce a dedicated semantic naming scanner, naming linter, or additional CI enforcement framework for this rule.

## 4. Worktrees and Delegation v3

- **Each implementation task uses an isolated Git worktree and a dedicated task branch.** Read-only task planning and approval may use a verified repository checkout before the task worktree exists. Once bootstrapped, verify a clean starting state for a new task. When resuming, preserve verified in-progress task changes and exclude unrelated work.
- **Narrow remote-only documentation path.** A ChatGPT-authored GitHub-only change may omit a local worktree only when it is a genuinely trivial documentation or metadata edit with no substantive effect on policy, security boundaries, workflow behavior, or executable instructions. Judge the change by its meaning, not its file extension. Record affirmative task evidence that the work happened remotely and inspect accessible task records for known local artifacts. Do not require proof of global nonexistence or claim that unverified local cleanup was completed. This path keeps direct source inspection, independent review, applicable CI, and merge authorization.
- **Default sequence: plan first, bootstrap second.** ChatGPT prepares a Codex Plan-mode prompt with the accepted issue, verified source revision and expected implementation baseline, proposed branch/worktree identity, and exactly one designated bootstrap owner. Codex Plan mode performs read-only investigation and returns a proposed plan. It must not create or change files, branches, worktrees, MCP configuration, or delegation artifacts, and must not claim that proposed task isolation already exists. ChatGPT reviews and approves the plan before implementation.
- **Execution-mode bootstrap.** After plan approval (or after scope verification when no separate Codex plan was produced), the designated bootstrap owner creates the isolated worktree and task branch in Codex Agent/execution mode (or ChatGPT creates them using an authorized capable tool). Codex reuses an explicitly supplied existing worktree after verification. Before modifying implementation files or binding worktree-scoped Delegation v3, verify the actual repository/root, worktree, branch, baseline commit, current HEAD, cleanliness for a new task, and registered identity where needed. Recompare these facts with the approved plan; if material drift invalidates its assumptions, stop for ChatGPT reassessment instead of silently applying the plan to a different baseline.
- **Optional pre-plan bootstrap.** An explicit authorized execution-mode step may create the worktree before planning when read-only inspection is insufficient or isolation is specifically required. It remains a separate step, never an instruction embedded in a Codex Plan-mode prompt. Whether planning comes first or not, no implementation starts before any produced plan receives ChatGPT approval.
- **Conditional Xcode MCP bootstrap.** Run this workflow only when the approved task requires Xcode MCP, after verifying the execution-mode task worktree and before the first workspace-dependent MCP operation. Tasks that use only native `xcodebuild`, `swift test`, or other repository-native commands do not need MCP initialization or authorization. Run native commands from the verified task worktree, bind their arguments to that worktree, and record their command, working directory, and result separately from MCP checks.
  - **Discover and select.** Resolve the worktree root canonically. Search for `.xcworkspace` and `.xcodeproj` candidates only beneath it; resolve symlinks and retain only canonical paths equal to or beneath the root by path components. Do not use string-prefix checks. Treat a `.xcodeproj/project.xcworkspace` as project-internal metadata, not as a competing application entrypoint, unless repository documentation or an explicit owner choice identifies that valid nested workspace for the task. For the requested operation, use a documented entrypoint when it resolves to one contained, selectable candidate. If documentation selects none and exactly one selectable entrypoint remains, use it and record why it is the unique candidate. If documentation or discovery leaves several genuine entrypoints, report them and wait for an explicit owner choice. An owner may resolve that ambiguity without editing repository documentation; record the choice and its rationale. A documented path outside the task worktree is a conflict: report it and do not silently substitute an in-worktree candidate. The owner may explicitly choose a contained candidate; record both the conflict and that choice.
  - **Verify workspace identity.** Inspect installed Xcode MCP schemas and confirm that a supported operation accepts the selected candidate type and can return or resolve its identity. Use the existing configured client to open the selected absolute path. If no supported operation can deterministically open and identify that workspace or project, report the limitation and block the MCP operation; do not substitute another candidate. Capture the returned `workspaceIdentifier` and associated path; if the open result omits a path, resolve that exact identifier through the supported workspace-list operation. Verify that the canonical returned path matches the selected candidate inside the task worktree. Do not infer identity from MCP reachability, the active Xcode window, or a default workspace.
  - **Scope and record.** Explicitly pass the verified `workspaceIdentifier` to every later workspace-scoped operation whose installed schema supports it. Block operations whose target cannot be bound deterministically. Record the absolute worktree root, branch, selected path, selection rationale, workspace identifier and path, and operation evidence in the existing task record. Keep native command results separate; a passing native check does not change an unavailable or failed MCP check to PASS.
  - **Owner boundary.** Ordinary access through the existing configured Xcode MCP client is allowed, including system-managed on-demand service activation. When that access opens and verifies the new worktree, proceed without waiting for owner acknowledgement or a manual GUI open. Codex must not start, stop, restart, reload, kill, reconnect, or otherwise manage the MCP server lifecycle directly or through scripts or commands. Do not change machine-wide Xcode MCP authorization or configuration, or enable `--unsafe-always-allow-all-agents` or other unsafe global permissions. If MCP authorization or service access fails, give the owner the exact worktree and selected project paths, the applicable owner action, and the affected blocked or unavailable checks. When applicable, the safe owner action is `open -a Xcode "<absolute selected path>"`. Continue independent native work where its target can be verified; resume Xcode MCP work only after the owner action and renewed authorization and workspace-identity verification.
- For MCP root registration and configuration maintenance, Codex discovers and verifies the exact **active MCP configuration file**, changes only authorized entries, preserves unrelated configuration, and performs static/offline validation. If the active config cannot be identified or safely updated, stop and ask the owner; do not modify a guessed file or claim an unverified registration is active.
- **MCP server lifecycle is owner-only.** Codex must never start, stop, restart, reload, kill, reconnect, replace, or otherwise manage the MCP server, directly or indirectly through scripts, process managers, tunnel wrappers, or tools. This prohibition also applies when registering/removing roots, applying configuration changes, recovering access, or troubleshooting a stale server view. When a configuration change requires a restart, Codex reports **`MCP RESTART REQUIRED — OWNER ACTION`**, the exact configuration path, changed entries, static validation outcome, and pending MCP-dependent verification. The owner performs the restart and reconnection. Codex may resume read-only verification of the server's recognized configuration only after the owner confirms availability; until then, report the change as configured but not activated.
- Prefer Delegation v3 bound to the actual worktree. Use manual Codex execution by default until a queued runner is reliable. Use native corrective lineage where supported. If native registration, task materialization, or corrective lineage is unavailable, use a cross-referenced manual contract with the real source identity, scope, criteria, results, and review evidence.
- Do not fabricate lineage or attestations, use an unrelated identity, bypass access controls, or make provenance-only limitations an artificial merge blocker.

## 5. Validation and coverage

- Use repository-native build, lint, typecheck, static-analysis, test, and physical-qualification checks. When MCP validation cannot execute a valid command, run the native equivalent and preserve its evidence.
- Aim for **90% meaningful coverage of testable first-party code**, especially new or substantially changed code. This is a target, not an unconditional numerical merge gate. Report the metric, scope, and exclusions; important missing behavior remains a concern at any percentage. Do not create brittle tests for coverage theater.

## 6. Independent review

- Every change requires independent review and direct ChatGPT inspection of the source and tests. Cumulative review must cover the final implementation and correction deltas. Targeted follow-up is acceptable when earlier evidence remains valid. The independent reviewer must not author approved changes.
- Tell the independent reviewer to inspect task-independent implementation names and paths under §3, including the purpose-based task-record exceptions. Worktree contents are in scope. Require correction of candidate-introduced violations before merge; unrelated tracked debt remains separate from slice readiness.
- A confirmed P0/P1 defect that is introduced or materially worsened by the candidate, or is included in the accepted task scope, **cannot be waived**. Fix it or factually disprove it before merge. Unrelated pre-existing defects do not automatically block.
- Material in-scope P2 findings require fixes. Justified unrelated or out-of-scope deferral is allowed. P3 findings are advisory unless evidence warrants elevation. Do not reclassify a true P1 merely to merge.
- Corrections ordinarily stay on the same worktree and PR. Create a new corrective delegation only when warranted or required by the tool.
- Use evidence-driven debugging; do not make indefinite speculative retries.

## 7. CI and integration context

- New executable-code projects have CI. The first task under this process in an existing repository must integrate applicable existing local suites into CI when they are inadequate.
- CI onboarding means the intended suites actually run successfully. A green but skipped or misconfigured job is insufficient. Process-required checks apply even without branch protection. Track hardware or unavailable-platform gaps explicitly.
- Required CI covers final PR changes in the applicable integration context. Record the PR HEAD and the actual tested head, test-merge, or merge-group SHA; verify that the assessed changes and relevant target state are current before merge. A change invalidates only affected review and validation, which must be refreshed proportionately.
- Investigate CI infrastructure failures and flakiness. Local Cubic quota exhaustion alone is not blocking when independent local review is complete.

## 8. Merge readiness

- ChatGPT must be able to inspect the source directly through MCP or GitHub. It reviews the final implementation and integration, PAC/TAC status, validation and coverage, cumulative independent findings, actual CI execution, qualifications, risks, and exceptions.
- Readiness verdicts are **READY**, **BLOCKED**, or **READY WITH EXPLICIT EXCEPTION**. The P0/P1 rule in §6 is non-waivable. Administrative-only provenance limitations may be accepted with alternative evidence.
- ChatGPT determines technical readiness. The owner explicitly authorizes merging, including through “merge” or “close this out.”

## 9. Exceptions and qualification

- Merge permission is not a substantive waiver. Identify each unmet requirement, residual risk, permitted scope, and follow-up. A failed check remains failed; an unrun check remains unverified, even if integration is authorized.
- Distinguish integration from product, hardware, and release qualification. Keep every deferred criterion’s ID, content, rationale, and status open, or move it to a linked issue without losing the obligation.
- Transferring already-authorized tracking is bookkeeping. Changing accepted scope or deferring a substantive requirement requires owner authorization; existing authorization may suffice.
- Exceptions never waive a confirmed in-scope P0/P1 defect, required direct source access, actual independent review, or an approved security boundary. A separately approved architectural revision may intentionally change the approved design; that is not a waiver.

## 10. PR and review feedback

- Codex may publish draft PRs after local checks, but may not merge them. ChatGPT checks feedback and CI when a PR is published or updated, when the user requests review feedback, and before merge. It adjudicates valid in-scope findings, false positives, and out-of-scope follow-ups.
- Do not continuously monitor a PR unless monitoring is configured.

## 11. Merge/closeout/cleanup

- After an authorized merge, verify the merge commit and applicable validation. If required post-merge checks are pending or failed, keep closeout open and report `MERGED — CLEANUP PENDING` with the blocker. Do not give destructive cleanup instructions until the checks pass. Investigate failures rather than automatically reverting, and do not require a new post-merge pipeline unless an existing requirement calls for one.
- After those checks pass, synchronize an eligible primary `main` checkout as part of post-merge cleanup. This safe fast-forward is required without a second owner approval; it does not authorize implementation in the primary checkout. A verified remote-only task with no primary checkout is not applicable.
  - Verify the primary checkout root and repository identity, and confirm its configured `origin` points to the intended repository. Require a successful fetch using the configured credentials; do not add an authentication mechanism.
  - Require the current branch to be `main` and the index and tracked/untracked working tree to be clean. Inspect ignored paths for overwrite risks. Preserve ignored files that do not conflict with the update.
  - Fetch `origin` successfully, record the local and fetched SHAs, and verify `git merge-base --is-ancestor HEAD origin/main`. If the SHAs match, report a verified no-op with the primary root, branch, equal SHAs, and action; do not run the merge.
  - Immediately before the merge, recheck the primary root and repository identity, current branch, index and tracked/untracked cleanliness, configured `origin`, fetched `origin/main` SHA, ancestry, and incoming paths against ignored files. If any check has changed or cannot be verified, preserve the checkout and report the blocker.
  - When local `HEAD` is a strict ancestor of fetched `origin/main`, run `git merge --ff-only --no-overwrite-ignore --no-autostash origin/main` from the verified primary root. The command must preserve conflicting ignored files and must not stash local changes. No additional approval is required when the preconditions pass.
  - After a fast-forward, verify that `HEAD` equals fetched `origin/main`, the branch is still `main`, the tracked/untracked working tree remains clean, and pre-existing ignored data remains intact. Report the primary root, branch, before/fetched/final SHAs, and action. For a no-op, report the root, branch, equal local/fetched SHAs, and verified no-op action.
  - If identity, cleanliness, fetch, ancestry, or overwrite safety cannot be verified, preserve the checkout and report the exact blocker and available SHAs as `MERGED — CLEANUP PENDING`. A failed protected merge is blocked, not inapplicable. Keep the issue open until the required synchronization is verified or the verified remote-only exception applies. Do not claim synchronization or cleanup completion. Do not use reset, force movement, rebase, stash, or branch switching as a workaround.
- Close the issue when its accepted scope is complete. Keep a durable record of accepted behavior, rationale, reviewed and tested revision, remaining obligations, and exceptions outside a disposable worktree.
- Reconcile repository-wide naming cleanup against the exact integrated revision. Close the repository-wide cleanup obligation only after reconciliation confirms that every confirmed violation has been resolved or covered by an explicit owner-approved policy exception. Outstanding compatibility migrations remain part of the open cleanup obligation. Report approved exceptions and inspection limitations explicitly in the completion statement.
- Determine the original implementor from task or delegation provenance. A commit author or merge actor alone does not establish who implemented the task, and a PR alone does not establish that a local worktree exists. If provenance or artifact state is unclear, report it as unverified and `MERGED — CLEANUP PENDING` with the missing evidence. Retain any known worktree, make no cleanup-complete claim, and give no destructive instructions.
- Before deleting a worktree, verify its repository, root, branch, and integration, then preserve valuable unmerged or uncommitted changes and sole-copy evidence. Retain the worktree when cleanup safety is uncertain and report `MERGED — CLEANUP PENDING` with the missing proof.
- When Codex implemented the task and post-merge cleanup is eligible, include a task-specific, pasteable Codex cleanup prompt in the merge response without waiting for another request. Name the verified repository, worktree root, branch, and PR/merge identity. Direct Codex to re-verify them, preserve valuable changes and sole-copy evidence, and remove only verified task-local artifacts and registrations where safe.
- When ChatGPT implemented the task, ChatGPT handles applicable cleanup. For a verified remote-only documentation change that meets the narrow §4 rule, inspect accessible task records for known local artifacts, verify issue and check state and relevant remote branch housekeeping, then report that no local cleanup is applicable. State which records were checked; do not claim global absence of artifacts. Do not invent or require a local worktree, branch, MCP registration, or Codex cleanup handoff.
- If a worktree is intentionally retained for chained work, state the reason and defer its cleanup prompt until cleanup becomes eligible. Keep the worktree and report the retention as intentional.
- When safe, remove the exact worktree and MCP root registration. MCP registration removals and their restart handoffs follow the owner-only lifecycle in §4. If a tool cannot perform an authorized cleanup action, provide verified exact terminal commands. Never use broad destructive cleanup without guards.

## 12. Distribution/pinning

- The single canonical public repository, [danielbyon/development-process](https://github.com/danielbyon/development-process), holds policy, decision records, focused Skill source, templates, and installation and update guidance.
- The three focused Skills are:
  - **development-orchestrator:** ChatGPT planning, delegation, and plan review.
  - **development-review:** ChatGPT source review, review adjudication, readiness, and merge guidance.
  - **delegation-executor:** Codex worktree and delegation setup, implementation, validation, and PR preparation.
- Skills operationally adapt the canonical policy; they do not duplicate its full governance text. Keep project-specific AGENTS.md instructions minimal and preserve native commands and constraints. Auxiliary Skills cannot override authority or gates; resolve conflicts explicitly.
- For new tasks, resolve the newest verified immutable published CalVer release and record that tag once. Verify its policy, tag, assets, native attestation and reconstructed provenance. Ignore GitHub's `latest` designation. An unverifiable newest eligible release blocks resolution; before the first release, return `NO_IMMUTABLE_RELEASE` rather than selecting a static SHA default.
- Existing tasks retain their recorded SHA or CalVer and Skill identity. Require exact installed-payload identity or explicit inspected compatibility evidence before applying a release. Unknown compatibility blocks. Do not silently apply newly installed Skills or repin ongoing tasks; migration requires explicit owner approval.
- Keep source, policy and trusted builder revisions separate in internal evidence. Policy-content equality alone does not establish approval. Release-specific Skill links are deterministic transformations of committed source, independently reconstructed during verification.
- One owner-triggered workflow qualifies, builds and publishes a complete draft as an immutable release. Qualification must establish independent full-diff/correction review, ChatGPT source/test inspection, required CI and owner merge authorization across all uncovered source and builder integrations. Structured readiness records locate actual evidence; unsupported assertions do not pass gates. For new ordinary admissions, schema-v2 receipts bind the exact provider records and content digests to the actual PR, reviewed head, provider timestamps and CI completion before merge. Later normalization may add only the actual merge SHA and integrated-commit membership to unchanged pre-merge evidence. Existing schema-v1 signed frozen releases remain verifiable; schema v1 cannot admit new evidence.
- The prospective first-release baseline is a separate trust origin. Admit only the exact corrected PR merge commit, with that commit as both source and builder and the policy revision derived independently. Require post-merge full-baseline review, direct ChatGPT source/test inspection and applicable CI before the owner's `admit-baseline` authorization, then record admission before the original release dispatch. Require zero ordinary integrations after the root and keep protected `main` at that exact commit through dispatch. Every later integration must meet ordinary chronology and coverage. The baseline grants no trust to ancestors, unrelated branches or equivalent trees. Design approval does not itself admit a production baseline or authorize release dispatch.
- Freeze original-run Pacific CalVer, source/policy/builder identities and qualification evidence. Verify all eight assets before publication. Preserve unknown drafts/tags and conflicting assets; recover only matching owned state. Correct published releases through a new CalVer, never by rewriting history.
- Administration-read verification access is a proposed owner-provisioned prerequisite, pending configuration and verification. Qualification is read-only. Ordinary publication uses Contents write; conditional Workflows write requires technical necessity and separate owner authorization. Never escalate automatically. CalVer tag protection is optional hardening.
- Implementation merge does not publish a release. The first release requires verified baseline admission, owner-configured prerequisites and separate owner dispatch; no additional per-release promotion PR is required. Preserve outstanding Issues #20/#22 distribution and live-qualification obligations until satisfied or formally transferred. Do not mark deployment complete from simulated evidence.
- Publication and activation are separate. Temporary staging preserves unrelated Skills and refuses drift or cross-policy migration. Production installation, global instruction changes, active-task migration and MCP configuration remain separately owner-controlled; the release workflow performs none of them.
- Authoritative records are: the issue for accepted scope; the task or delegation for execution and result identity; the review for findings and disposition; and the PR for integration and readiness summary. Link these records and do not create competing task state. See [Skill release operations](skill-releases.md) for evidence, recovery and bootstrap requirements.

## 13. Adoption and vocabulary

- Apply this process prospectively to all current and future projects; do not retroactively re-author historical delegations. Existing repositories adopt it at their next task and add adequate CI for local suites when needed.
- **next task:** inspect the repository, issues, and requirements and select the next approved slice. When a Codex plan is required, return only the read-only Plan-mode handoff. After review, `APPROVE` returns the execution/bootstrap handoff and `REVISE` returns only a plan-revision prompt. A verified straightforward task may use the no-plan path.
- **codex plan:** read the plan, specification, and actual repository evidence; explicitly approve or revise it. Approval returns one execution/bootstrap handoff. Revision returns only a correction prompt.
- **implemented:** inspect source, tests, and independent findings; determine corrections and readiness.
- **review feedback:** inspect PR reviews, triage findings, and prepare targeted corrections.
- **close this out:** subject to quality gates and explicit authorization, merge, verify applicable CI, and close the issue when its scope is complete. Determine cleanup ownership from task provenance and actual artifacts; follow §11 for Codex, ChatGPT, remote-only, pending, and retained-worktree dispositions.

## 14. Governance and initial bootstrap

- Substantive process changes require owner authorization. Technical Skill and documentation fixes follow the normal reviewed workflow.
- The initial repository bootstrap contract identifies exact unavailable prerequisites and the narrow accommodation. It does not waive source inspection, independent review, the P0/P1 rule, or truthful evidence. Reuse existing authorizations rather than adding ceremonial duplicate approval stages.
- Version 1 does not add centralized orchestration, redundant provenance, universal CI abstraction, a custom coordination framework, or fixed retry quotas.

## 15. Invariant

**Correctness and independently inspectable evidence are mandatory. Administrative completeness is not a substitute for correctness and must not obstruct otherwise valid work. No exception fabricates success, conceals defects, bypasses direct source inspection or independent review, or weakens an approved security boundary.**
