# Development review

Use this Skill for `implemented`, `review feedback`, readiness, `merge`, and `close this out` requests, and when the owner reports cleanup complete or requests post-closeout issue discovery. This Skill applies the pinned policy to review and closeout; it does not replace the policy or create a separate approval authority.

The issue defines accepted scope, and the pinned policy governs roles and process. If the governing policy reference is missing, malformed, or unresolved, stop the affected decision. If the issue, approved plan, or task instructions materially conflict with the pinned policy, state the conflict and stop for owner adjudication. A difference between installed Skill versions alone does not block an already approved task. This Skill does not expand scope or authorize an action by itself. The owner must explicitly authorize a merge for the current task.

## Policy and source access

For a historical task that adopts a cleanup amendment, use its qualified immutable release tag and the full policy revision resolved from that tag. Record both in existing task-bound cleanup evidence as the `cleanup_amendment` reference. Apply the amendment only to the historical pin's superseded cleanup provisions; the original task pin, provenance, and unrelated gates remain unchanged. For a historical manual task without a structured record, use existing task-bound evidence such as the issue, PR, approved plan, branch, and worktree identity. Creating, migrating, exporting, or preserving a worktree-local task record is not a cleanup prerequisite; no new task-record schema or migration framework is required.

For a new task, use the identity embedded in this Skill when it is active. Read the canonical policy at its recorded policy revision before applying it. For an already approved task, the identity in its approved handoff governs continuation. Different installed Skill versions alone do not block the task or change its policy identity. Stop when the governing reference is missing, malformed, or unresolved. If instructions materially conflict with the approved handoff or pinned policy, stop the affected decision and ask the owner to adjudicate. Do not select a newer release or resolve GitHub's `latest` label.

Release qualification remains separate from task admission. A successful owner-triggered workflow on reviewed and CI-approved merged `main`, followed by immutable publication, qualifies a release. The workflow retains its six qualification suites, deterministic packaging, provenance, signed attestation, and publication checks. Ordinary admission uses the active Skill identity and exact policy file; it does not inspect release assets, workflow records, or hosted session revision. It does not rebuild packages or reconstruct attestations. Keep `verify-release` for explicit audits and diagnostics.

Successful release qualification does not install this Skill. The user manually installs and updates released Skills in ChatGPT and Codex. Publication does not upload or activate them.

Continue an existing task with its recorded SHA or CalVer and source, policy and builder identities. Do not select a new release, repin or repeat release qualification during continuation. Preserve historical pins unless the owner explicitly approves migration.
- Verify the repository, issue, task identity, worktree, branch, baseline, HEAD, PR, and candidate paths from current evidence. Read relevant instructions and accepted specifications.
- Always inspect the candidate source directly through gpt-repo-local or the GitHub connection for the repository owner. Reports and summaries do not establish source-review evidence. If source is unavailable, return `BLOCKED` for readiness.
- Inspect applicable source-adjacent tests and validation evidence. If applicable tests exist but cannot be inspected, record them as `UNVERIFIED` and return `BLOCKED`. If no tests apply, such as for a documentation-only change, record that determination and its rationale and assess the applicable validation evidence. Do not block solely because no tests apply, and do not report absent or unrun tests as passing.
- Separate evidence from inference. Report unavailable or stale evidence as `UNVERIFIED` until checked.

- Verify bootstrap evidence records the exact task root enrollment disposition and rationale, including manual execution without enrollment. A supported `never-enrolled` disposition does not require MCP connectivity, and `UNKNOWN_REPO` is not proof. Check that later enrollment attempts or disposition changes update the same evidence.
- Require successful immutable publication and explicit owner adoption before applying a historical cleanup amendment. A release that is qualified but not adopted is not an adopted amendment; publication alone does not authorize amended cleanup. After adoption, record its qualified immutable release tag and the resolved policy revision in existing task-bound cleanup evidence as `cleanup_amendment`. Preserve the original task pin and provenance.

## Review a completed change

When the user says `implemented` or asks for readiness:

1. Read the accepted issue and approved plan. Verify the candidate identity and compare the complete change with accepted scope, exclusions, and the approved plan. Inspect final source, applicable tests, and validation evidence directly.
2. Check each PAC/TAC and required validation criterion. Record each as `PASS`, `FAIL`, `UNVERIFIED`, or `WAIVED` only when a real authorized waiver applies. Preserve the actual failure or unrun state when an integration exception is granted.
3. Verify a separate, non-authoring execution reviewed the full diff. Confirm that later corrections also received independent review and that the cumulative evidence covers the final candidate. The reviewer handoff must include the task-independent naming supplement below and state that worktree contents are in scope. Prefer local Cubic; use a separate Codex execution when local Cubic is unavailable. Do not assume a human review will occur. Cubic CI quota exhaustion does not block when independent local review is complete.
4. Assess findings against policy §6. Fix or factually disprove a confirmed P0/P1 defect that the candidate introduces, materially worsens, or includes in accepted scope. A true in-scope P0/P1 cannot be waived. Fix material in-scope P2 findings. Track justified out-of-scope P2 deferrals; report P3 findings as advisory unless evidence supports elevating them.
5. Inspect changed names, strings, comments, and paths under policy §3 and the task-independent naming supplement. Require correction of candidate-introduced violations within scope while preserving behavior and compatibility contracts. Unchanged, separately tracked legacy violations do not by themselves block a slice.
6. Report tests, meaningful coverage, scope exclusions, qualification gaps, review evidence, residual risk, and owner decisions. The 90% meaningful coverage figure is a target, not a standalone merge gate.

**Task-independent naming supplement (existing task pins remain unchanged): Scope includes types, functions, methods, variables, and constants; tests and fixtures; scripts and first-party generators; maintained technical documentation and source comments; logging, diagnostic, and configuration strings; and implementation-owned files and directories. Keep task IDs in purpose-based task records and preserve stable domain and protocol identifiers. Preserve compatibility-sensitive public APIs, persisted keys, serialized fields and data, wire formats, reflection-visible names, and dynamic string lookups; verify consumers before changing configuration, logging, or diagnostic strings. This supplement authorizes no behavior or compatibility change. Treat confirmed compatibility-sensitive changes as Tier 2 and require separate owner-approved migration scope.**

### Check PR integration evidence

- When a PR is published or updated, and before a merge, inspect its review feedback and actual check jobs and logs. Identify the suites and commands that ran, skipped, failed, or were misconfigured. A green workflow with a required skipped suite does not pass that requirement.
- Bind CI evidence to the exact PR HEAD, tested commit, and relevant target state. A synthetic merge SHA may differ from PR HEAD when its parents match the tested PR head and event base. If the PR head or relevant base changes, refresh the affected evidence.
- Refresh only evidence invalidated by a candidate or target change. Investigate infrastructure failures; do not report an unrun check as passing.

### Return a readiness verdict

Use exactly one verdict:

- `READY`: all mandatory gates pass.
- `BLOCKED`: a mandatory gate fails or remains unverified, source inspection or applicable test inspection is unavailable, or independent review does not cover the final candidate.
- `READY WITH EXPLICIT EXCEPTION`: the owner has authorized a policy-permitted integration exception, every non-waivable gate passes, and the report states the unmet criteria, evidence, residual risk, permitted scope, and follow-up.

Authorization does not change a failed or unverified criterion into a pass. A permitted exception cannot waive required source inspection, independent review, a confirmed in-scope P0/P1 defect, or an approved security boundary.

## Review PR feedback

When the user says `review feedback`:

1. Identify the current PR head and retrieve current and prior review threads, issue comments, and their resolution state.
2. Reconcile feedback as new, unresolved, addressed, resolved, stale, valid, false positive, or out of scope. Check the relevant code and accepted issue before deciding.
3. Fix valid in-scope defects through a focused, pasteable Codex correction prompt. Give evidence for false positives. Defer unrelated requests with traceable rationale instead of expanding the issue.
4. Preserve previous dispositions and review evidence. Require independent review of each correction delta and refresh only evidence affected by the change.

## Close out an authorized change

When the owner says `merge`, `close this out`, or gives another explicit merge instruction, treat it as merge authorization under policy §§8, 10, 11, and 13. Do not ask for redundant approval. That instruction authorizes the merge; it does not authorize a separate exception.

1. Independently determine current-head readiness from direct source and test inspection, independent review, required CI, issue scope, and policy. Merge only for `READY` or a `READY WITH EXPLICIT EXCEPTION` whose exception has separate owner authorization. If a mandatory gate fails or remains unverified, do not merge even when the owner authorized it.
2. Before merging, confirm the PR head, target branch, checks, and authorization still match the inspected candidate. ChatGPT may execute the merge under the owner's authorization. Codex does not approve or merge its own work.
3. After the merge, verify the merge commit and applicable checks. If required post-merge validation is pending or failed, keep closeout open, report `MERGED — CLEANUP PENDING` with the blocker, and give no destructive cleanup instruction. Close the issue only after required checks pass, accepted scope is complete, and §11's required primary-main synchronization has either completed as a fast-forward and passed verification or been verified as an already-current no-op. A verified remote-only implementation makes task-worktree cleanup inapplicable. Primary-main synchronization is inapplicable only when task-bound evidence verifies that the remote-only task has no primary checkout. If a primary checkout exists, complete all applicable §11 synchronization requirements. Unknown primary-checkout state does not establish an exception. If applicable primary-main synchronization is blocked or unverified, keep the issue open and block discovery; report `MERGED — CLEANUP PENDING` with the blocker. Keep deferred obligations tracked; close an issue only when its obligations are complete or formally transferred to an explicitly linked, authorized follow-up. Close a repository-wide naming cleanup only after reconciliation resolves every confirmed violation or records an explicit owner-approved exception. Keep outstanding compatibility migrations open, and report approved exceptions and inspection limits.
4. Determine the original implementor from task or delegation provenance. Use existing task-bound evidence such as the issue, PR, approved plan, branch, and worktree identity; a structured task record may not exist for a historical manual task. A commit author or merge actor alone does not establish implementor. If task identity or provenance remains unclear, report `MERGED — CLEANUP PENDING`, retain any known worktree, and give no destructive instructions or cleanup-complete claim. Do not require creating, migrating, exporting, or preserving a worktree-local task record for cleanup.
5. For an eligible Codex-implemented task, automatically include a task-specific, pasteable Codex cleanup prompt in the merge response. An otherwise eligible task with a pending fast-forward still receives the automatic prompt. If a known or unverified primary-checkout safety blocker prevents cleanup eligibility, report the blocker and withhold the prompt until eligibility is verified. Name the verified repository, worktree root, branch, and PR/merge identity. Direct Codex to follow the canonical process in §11 for primary-checkout synchronization and its verification. Explicitly keep the issue open until required primary-main synchronization is completed and verified, or a verified already-current no-op is recorded, and all other required closure checks pass. The prompt must include `git merge --ff-only --no-overwrite-ignore --no-autostash origin/main` for an eligible fast-forward, with no additional approval after §11's checks pass. Once cleanup checks pass, ordinary ignored content in the task worktree is disposable by default. This includes build output, dependency installations, temporary files, tool caches, and unknown ignored files; do not require proof or backup for each item. Preserve actual unintegrated source changes, identified unrelated user data, and explicitly designated durable data. Worktree-local qualification, review, `.chatgpt`, and bookkeeping records are disposable, including sole copies and untracked files. Follow the enrollment and guarded-removal checks below. Do not wait for a separate cleanup request.
6. For a ChatGPT-implemented task, ChatGPT performs applicable cleanup through supported, verified operations under the canonical process in §11. When its checks allow a primary-`main` fast-forward, run `git merge --ff-only --no-overwrite-ignore --no-autostash origin/main` without another approval. Do not generate a Codex cleanup prompt solely because the PR merged.
7. Use the remote-only path only for a genuinely trivial documentation or metadata edit with no substantive effect on policy, security boundaries, workflow behavior, or executable instructions. A Markdown extension alone does not establish eligibility. Require affirmative task evidence that implementation happened through GitHub, then inspect accessible records for known local artifacts. Do not require proof of global nonexistence. Verify issue and check state and relevant remote branch housekeeping; report `LOCAL CLEANUP INAPPLICABLE — REMOTE-ONLY DISPOSITION` only when the records support that conclusion, and state what was checked. This disposition applies only to task-worktree cleanup; primary-main synchronization follows §11. Never label this disposition `CLEANUP COMPLETE` or `MERGED — CLEANUP COMPLETE`. Do not invent or require a local worktree, branch, MCP registration, or Codex cleanup handoff.
8. If the owner approves retention of a verified task worktree for future work, treat it as a qualifying closeout disposition once all other required checks pass. Record the reason and deferred cleanup, keep the worktree intentionally retained, and run discovery immediately. Defer only its eventual removal and cleanup prompt. Do not report `MERGED — CLEANUP PENDING` or wait for worktree removal solely because it is retained. Reserve `MERGED — CLEANUP PENDING` for unsafe or unverified retention, unknown provenance, or other unresolved required verification.
9. Record the exact task worktree's enrollment disposition, supporting evidence, and rationale in cleanup evidence. Use three dispositions: `never-enrolled`, `registered-or-potentially-outstanding`, and `previously-registered-with-verified-removal`. `UNKNOWN_REPO` is not evidence of non-enrollment. An enrollment attempt with an unknown outcome remains potentially outstanding. A trusted registration for the exact task root overrides a prior `never-enrolled` finding. When reconciliation applies, use the correct stable repository ID and canonical root. A never-enrolled root requires no MCP connectivity, registry identity or backing-file discovery, active-root check, offline validation, or restart for cleanup. A registered or potentially outstanding root keeps the existing §4 registry, offline-validation, active-absence, and owner-only lifecycle requirements. After any owner handoff, verify again which registry file the running instance uses; immediately before deletion, recheck its exact entry and active absence and confirm offline validation applies to the current file. Reuse verified prior removal evidence when it applies to this root and no contrary evidence or credible drift exists; an attempted removal or unverified absence is insufficient.
10. Try ordinary exact-target removal first with `git worktree remove -- <canonical-task-root>`. A single `--force` is permitted only when ordinary removal refuses exclusively because of eligible disposable content. Immediately before force removal, reverify target identity, integration, applicable registration disposition, protected-data boundaries, and the absence of unrelated changes. Locked worktrees, ambiguous refusals, permission errors, and unexpected conditions do not permit force removal. Never use double force or broader filesystem deletion. If the refusal has another or unclear cause, retain the worktree and report `MERGED — CLEANUP PENDING`. A required registry restart remains owner-only; report `MCP RESTART REQUIRED — OWNER ACTION` and wait for owner confirmation before checking active roots.
11. After removal, verify that the exact worktree path is absent. Remove only the integrated task branch by its exact name and verify that it is absent. Post-cleanup verification follows the recorded enrollment disposition: do not add registry checks for a never-enrolled root; verify applicable registration removal for a registered or potentially outstanding root; and accept verified prior removal unless contrary evidence or credible drift invalidates it. Eligibility does not establish successful removal. If either removal fails, retain the remaining resource and report the exact failure without widening the target.

- Verify the resolved target remains inside the exact task root before destructive operations, using path-component containment. Do not follow symlinks into external resources or delete filesystem paths outside the verified root. Keep this check proportionate; do not inventory artifacts or require regeneration proofs.
- Before reporting cleanup complete, verify filesystem-path absence and Git worktree-registration absence for every task worktree. Verify that only an integrated local branch was removed with ordinary `git branch -d` and that it is absent. Leave cleanup pending while a registration remains, integration is unverified, or removal fails; do not run `git worktree prune` or force-delete a branch. For MCP, do not add unconditional registry checks for never-enrolled; use existing checks for registered or potentially outstanding roots; reuse verified prior removal evidence unless contrary evidence or credible drift appears.

## Post-closeout issue discovery

An owner's cleanup-completion report triggers applicable verification first. The report alone does not establish that cleanup passed.

Run discovery only after required cleanup and applicable primary-main synchronization have been verified. A verified remote-only implementation makes task-worktree cleanup inapplicable; primary-main synchronization is inapplicable only when task-bound evidence verifies that the remote-only task has no primary checkout. Unknown primary-checkout state does not establish an exception. For owner-approved intentional retention, run discovery immediately after all other required checks pass. Record the retention reason and deferred cleanup.

Keep discovery blocked while applicable primary-main synchronization is pending, blocked, or unverified; while required checks are pending; for unknown provenance; while applicable registration or restart verification remains unresolved; or for unsafe or unverified retention. A never-enrolled disposition adds no registry checks, and verified prior removal remains sufficient unless contrary evidence or credible drift invalidates it.

Record the closeout result before discovery. Then invoke the `development-orchestrator` Skill's post-closeout issue discovery procedure. Pass the repository identity, merge and issue identities, verified cleanup disposition, recorded policy pin, task source identity, and inspected source revision. Report retrieval failures separately. A discovery failure does not reopen the closeout result.

Closeout-triggered discovery ends this review invocation after one report. Do not offer or recommend preparing a task, Plan-mode handoff, or bootstrap. Do not echo prospective task-preparation details from shared input, including a proposed branch, worktree, or bootstrap owner. Mention an existing worktree or branch only when it supports eligibility or concurrency evidence. The owner may choose to handle a recommendation in a separate session.

## Response format

Keep the report tied to the exact candidate revision. State the verdict, evidence, findings and dispositions, check statuses, owner authorization, residual risk, and next action. For `review feedback`, include the targeted Codex prompt when corrections are needed. For closeout, report the merge commit, issue state, applicable checks, and cleanup disposition. For a verified remote-only disposition, state `LOCAL CLEANUP INAPPLICABLE — REMOTE-ONLY DISPOSITION`; never label it `CLEANUP COMPLETE` or `MERGED — CLEANUP COMPLETE`. For closeout-triggered discovery, this terminal rule overrides the generic next-action field: omit any next action that would propose planning or implementation. Do not offer or recommend preparing a task, plan, or bootstrap. The owner may choose a separate session.

## Release readiness evidence

For release qualification, provide an index into actual issue, task/delegation, independent-review, inspection, CI and owner-authorization records. Include repository/PR identity, reviewed head/base and integration result, review ranges and correction coverage, source/test inspection identity, CI run/attempt and tested revision, and explicit owner merge authorization. Link inspectable original records and identify their provenance. Booleans or a readiness summary cannot establish another execution's review or authorization.

Verify every uncovered integration from an applicable admitted baseline through the selected source, and separately through the builder. Cover complete changes. For squash/rebase integration, verify tree, range and parent relationships instead of requiring identical commit IDs. Import genuine historical evidence without inventing structured records retrospectively. Missing, contradictory or stale mandatory evidence blocks publication. A candidate baseline is not admitted until its evidence passes; it cannot confer trust backwards onto older source. Reuse existing authoritative records without requiring cosmetic edits to old PRs.
