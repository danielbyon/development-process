# Decision record

This record summarizes foundational v1.0 decisions and subsequent owner-approved amendments. The contract in [docs/PROCESS.md](PROCESS.md) remains authoritative.

## Provenance

Issue #1 states that the owner approved v1.0 after a 50-question governance interview and two external review passes. It does not include the individual questions and answers or identify the external reviewers. This record preserves the stated provenance without inventing missing interview or reviewer details.

The issue also identifies three final amendments: tasks use an isolated worktree and dedicated branch; one predicate makes confirmed in-scope or candidate-introduced/materially-worsened P0/P1 defects non-waivable; tasks and Skills pin the current owner-approved immutable policy revision.

## Decisions and rationale

1. **Keep one canonical private policy source.** Project instructions and focused Skills adapt the canonical policy rather than copying the full governance text. This keeps policy authority and change history in one place.
2. **Separate requirements, execution, review, and integration records.** The issue is authoritative for accepted scope; the task or delegation for execution and result identity; the review for findings and disposition; and the PR for integration and readiness. Linking these records avoids competing task state.
3. **Require independent review for every change.** A separate non-authoring review execution and direct ChatGPT inspection preserve review independence even for small documentation changes. Local Cubic is preferred; a separate Codex review execution is the fallback. Cubic CI review is supplementary.
4. **Make the P0/P1 rule non-waivable within its defined scope.** A confirmed P0/P1 defect introduced or materially worsened by the candidate, or included in accepted scope, must be fixed or factually disproved before merge. Unrelated pre-existing defects do not automatically block.
5. **Treat 90% meaningful coverage as a target, not a numeric merge gate.** Report scope and exclusions, and do not write brittle tests to inflate coverage. Missing important behavior still matters at any measured percentage.
6. **Validate in the real integration context.** Required CI must execute checks on the final PR changes and record the tested integration revision. A green skipped or misconfigured job is not evidence of success. Qualification gaps remain distinct from integration.
7. **Allow a narrow, truthful bootstrap accommodation.** An empty root commit may establish an otherwise unborn main branch. It does not authorize unreviewed substantive changes on main or waive source inspection, independent review, the P0/P1 rule, or truthful evidence.
8. **Keep implementation and governance proportional.** The contract rejects centralized orchestration, redundant provenance, universal CI abstractions, a custom coordination framework, and fixed retry quotas in v1. Manual Codex execution remains the default until queued execution is reliable; native worktree-bound Delegation v3 is preferred when available.
9. **Preserve obligations when work is deferred.** Record criterion identifiers, content, rationale, and status; transfer tracking only when authorized. Distinguish merge permission from a substantive waiver and keep failed or unrun checks truthful.
10. **Scope Issue #1 to the repository foundation.** Do not implement or install the three Skills or an installer here. Existing follow-up issues #2–#5 own those slices. The policy must have an owner-approved immutable commit revision before Skills are distributed.
11. **Adopt prospectively and clean up only with evidence.** Do not rewrite historical delegations. Before deleting a worktree, prove that no valuable unmerged work or sole-copy evidence would be lost.

12. **Owner-controlled MCP lifecycle (Issue #7, approved 2026-11-10).** Codex is responsible for locating and safely updating only the active MCP configuration, validating changes statically, and reporting the exact file, changes, validation, and pending checks. The owner alone restarts and reconnects the shared MCP server. **Rationale:** autonomous restarts can interrupt active MCP connections, ChatGPT/Codex sessions, and unrelated tasks. **Rejected alternative:** Codex-initiated lifecycle actions, directly or through scripts, tools, or recovery wrappers, even for stale registrations, failed connections, and cleanup. **Failure modes:** editing an inactive config, damaging unrelated entries, disrupting active connections, and falsely treating the old server view as proof of activation. A configuration change remains pending until the owner restarts/reconnects; Codex then performs read-only verification.

13. **Plan first, then worktree bootstrap (Issue #12, approved 2026-11-11).** Read-only Codex Plan mode may inspect a verified checkout before a dedicated task worktree exists; after ChatGPT approves the plan, one designated executor establishes and verifies isolation in Agent/execution mode before source edits or worktree-bound Delegation v3. **Rationale:** Codex Plan mode cannot create a worktree, so combining bootstrap and planning in its first prompt causes an impossible instruction and an ordering race. **Rejected alternatives:** force a preliminary Agent-mode worktree creation for every task, allow Plan mode to mutate Git or MCP configuration, or approve implementation against an unverified/mismatched baseline. **Failure modes:** fabricated worktree identity, primary-checkout mutation, binding V3 to the wrong root, silent post-plan baseline drift, and premature implementation. **Invariant:** a plan can be approved without a worktree, but no implementation can begin without verified isolation; existing task pins and owner-only MCP restart authority remain intact.

## Rejected alternatives and constraints

The approved contract explicitly declines duplicated full policy text in Skills, a new central coordination system, a universal CI layer, retroactive rewriting of prior work, fixed retry quotas, and coverage theater. It also rules out fabricated delegation lineage, access-control bypass, reclassification of true P1 findings to permit merge, automatic merge, and broad destructive cleanup.

Changes to product scope, architecture, security trade-offs, substantive exceptions, or substantive policy require owner authorization. Routine technical choices remain within the accepted design; this decision record does not broaden those authorities.

## Known limitations

The Issue #1 foundation slice created no application code, test suite, or Skill implementation. Issue #5 later added Skill distribution tooling and executable checks. Its package and staging tests do not exercise the live ChatGPT upload UI or LLM behavior.

## Issue #5: Skill packaging and distribution

14. **Pin distributed Skills to the approved policy revision.** The distribution manifest sets policy revision `aa8dc7784641dd5416befdebc246ed081bfd7ade`. Each Skill links to that immutable policy copy. Package provenance records the actual source commit in a separate field. Existing tasks keep their recorded policy and Skill revisions; staging does not migrate them.

15. **Build one archive per Skill with verified source provenance.** OpenAI's official validator checks Skill frontmatter. The repository adds a small deterministic ZIP builder because the validator does not establish archive reproducibility or Git-backed source provenance, and the approved output consists of three individually installable Skill archives. The ZIP contains one Skill directory with `SKILL.md` and `agents/openai.yaml`. A sidecar outside the ZIP records the policy revision, actual source commit, included source paths, payload hashes, and archive hash. Payload hashes cover the ZIP members only; the sidecar is not included in its own hash set. Verification checks the manifest and each payload against the declared Git commit.

16. **Stage Skills separately from production.** The staging command writes to the explicit staging root's `.agents/skills` directory, outside the source repository. An explicit initialization command marks an empty temporary root before installation. It supports first installation, idempotent repeat, and an explicit same-policy upgrade. It refuses unknown installs, local drift, policy mismatch, and policy migration. It does not select a project or personal production target. Promotion remains a manual owner action after reviewing the staged files.

17. **Keep product checks tied to their evidence.** CI runs the official validator, distribution tests, workflow-contract checks, and a temporary Codex-compatible staging smoke test on the PR integration revision. It builds provenance-verified packages from a separate checkout at the exact PR source revision, even when the merge result includes non-conflicting changes from the base branch. Those tests do not establish LLM behavior or successful ChatGPT UI import. The three standalone archives use the supported Skill upload workflow; eligibility, workspace permissions, scanning, and any review decision remain controlled by ChatGPT.

The detailed Q1–Q50 interview record and the external review reports are not included in Issue #1. Their absence is recorded rather than reconstructed.

## Issue #20: planning handoff, cleanup, and distribution follow-up

19. **Separate planning from execution handoff (Issue #20; builds on decision 12).**
   - Rationale: The approved Issue #20 plan puts ChatGPT review before execution when a Codex plan is required. Decision 12 records that Plan mode cannot create a worktree, so bootstrap must happen in a separate execution-mode step after approval.
   - Rejected alternatives: Embedding bootstrap instructions in the Plan-mode prompt asks Plan mode to perform an unavailable operation. Returning an execution handoff before ChatGPT reviews the plan starts work against a plan that may still need correction.
   - Failure modes: Premature edits, instructions that Plan mode cannot carry out, delegation tied to a worktree that does not exist, competing bootstrap owners, and silent use of a baseline that has materially drifted.
   - Invariants: `next task` returns only a read-only Plan-mode prompt when planning is required. `APPROVE` returns one execution/bootstrap handoff; `REVISE` returns only a correction prompt. A verified straightforward task may use the no-plan path. Keep one bootstrap owner, verify isolation and task identity before edits, and stop for reassessment when material drift invalidates the approved plan.
20. **Assign cleanup from task provenance and verified artifacts.**
   - Rationale: The approved Issue #20 plan ties cleanup ownership to implementation provenance and task-specific artifacts. Task or delegation records identify who implemented the change and which worktree belongs to the task. Commit authorship and merge activity describe later repository events.
   - Rejected alternatives: Assigning cleanup to the latest commit author or merger cannot establish who created or owns the task worktree. A PR alone does not show that a local worktree exists. Treating every GitHub-only edit as cleanup-free would also exceed Issue #20's narrow exception.
   - Failure modes: Cleanup assigned to the wrong party, lost task changes or sole-copy evidence, false claims that cleanup is complete, and behavioral policy or Skill edits bypassing the accepted review path because they are Markdown or remote-authored.
   - Invariants: Determine the original implementor from task provenance. Verify available artifacts and cleanup safety. Allow the remote-only path only with affirmative evidence of remote execution and trivial semantic impact on documentation or metadata; inspect accessible task records for known local artifacts without asserting global nonexistence. Keep unknown or unsafe cases pending, retain intentionally held worktrees, and preserve the owner-only MCP restart and reconnection rule from decision 12.
21. **Keep distribution as a separate, owner-controlled stage.**
   - Rationale: The approved Issue #20 plan leaves distribution pins and deployment out of the implementation PR. After merge, the owner approves the exact immutable policy revision for new task distribution. The Skill source commit identifies packaged Skill files; it does not establish policy approval. Decision 18 keeps those revisions separate and preserves active tasks' historical pins.
   - Rejected alternatives: Pinning an unmerged or hypothetical revision cannot identify the canonical policy that will be approved after merge. Using the Skill source commit as policy approval conflates two revisions. Migrating active pins changes the policy those tasks accepted, and deployment before package checks, independent review, or owner approval skips required gates.
   - Failure modes: Distribution of an unapproved policy, inaccurate package provenance, changed rules in active tasks, and premature completion of Issue #20 while promotion remains outstanding.
   - Invariants: Keep policy and source revisions distinct, preserve historical pins, validate and stage packages built from the reviewed Skill source against the actual approved policy revision, and leave activation under owner control. Track promotion under Issue #20 or an explicitly linked and authorized follow-up. Do not mark all acceptance criteria complete until promotion is done or the remaining obligation is formally transferred.

## Issue #23: task-independent implementation naming

22. **Keep implementation names independent of temporary task identity (Issue #23, owner-approved 2026-11-12).**
   - Rationale: Source, tests, and implementation paths should describe enduring behavior or domain concepts. Task identifiers remain useful in issues, plans, ADRs, evidence, branch and worktree labels, and other records whose purpose is task tracking. Purpose-based exceptions preserve that traceability without tying implementation names to the task that introduced them.
   - Rejected alternatives: Allowing an approved plan to grandfather a task-derived name carries temporary labels into long-lived code. Renaming every occurrence of an issue identifier would erase legitimate task records and meaningful protocol or domain versions. Automatically renaming persisted or externally consumed names risks compatibility failures. A new naming scanner, linter, or CI framework would add enforcement beyond the approved scope.
   - Failure modes: Task-specific names become misleading after the task ends; broad renames break persisted or external contracts; comments lose the rationale needed to understand a constraint; and unrelated historical debt blocks otherwise ready changes or disappears from tracking.
   - Invariants: Use task-independent names for implementation symbols, test identifiers, and implementation paths, including contents of task-named worktrees. Preserve task IDs in purpose-based task records and coordination labels, and preserve real domain terms and numeric identifiers. Tier 1 permits evidence-based, behavior-preserving coordinated renames of internal names. Tier 2 compatibility migrations need separate owner-approved scope. Check candidate changes through author self-review and the existing independent review. Correct candidate-introduced violations before merge while tracking unrelated debt separately. Reconcile repository-wide cleanup against the integrated revision; resolve every confirmed violation or record an explicit owner-approved exception, and keep outstanding compatibility migrations open.
   - Rollout obligations (separate from this implementation PR):
     1. After merge, identify the actual immutable policy revision and obtain explicit owner approval for that exact revision before distributing it.
     2. Promote the updated Skills in a separately reviewed release. Preserve Issue #22's approved pin and scope; do not change either as part of Issue #23.
     3. Before changing global Codex instructions, verify the effective `CODEX_HOME`; precedence between global `AGENTS.md` and `AGENTS.override.md`; applicable project-level instruction conflicts; instruction size limits; and actual instruction discovery and activation.
     4. Qualify the behavior in fresh sessions with a prohibited task-derived internal helper, a legitimate domain or protocol identifier, and a compatibility-sensitive persisted key.
     5. Supply the naming rule and its purpose-based exceptions to non-authoring reviewers.
     6. Give active tasks supplementary guidance at their next plan-review or implementation-correction handoff. Preserve their existing policy pins and historical evidence.
     7. Keep production activation and global configuration changes under separate owner authorization.
   - Exclusions: Issue #23 defines policy and review practice. It does not authorize a repository-wide cleanup, a compatibility migration, a dedicated semantic naming scanner, a naming linter, or an additional CI enforcement framework. This PR records rollout obligations only; it does not promote Skills, edit global instructions, or activate configuration.

## Issue #32: release evidence chronology and prospective baseline

The owner approved implementation planning for both ordinary evidence chronology and a prospective first-release trust root on 2026-11-16. That approval establishes the design only; it does not admit a production baseline, qualify earlier PRs, authorize merge or dispatch, or publish a release.

- **Rationale:** The previous controller checked declared roles, ranges, hashes and CI identity, but a later owner-authenticated summary could not prove that the referenced review, inspection, authorization or successful CI existed before the PR merged. The first release also needs an explicit root that does not pretend to have ordinary historical evidence.
- **Ordinary evidence:** New admissions use schema-v2 original receipts tied to exact GitHub records, PR identity, reviewed bytes, and provider `created_at`/`updated_at` times. The complete independent review chain, ChatGPT inspection, owner merge authorization, and selected successful CI job must predate the actual `merged_at`. Full reviews and contiguous correction deltas retain all findings and dispositions. Post-merge normalization can add only provider-confirmed merge identity and commit membership to unchanged pre-merge evidence; the normalization timestamp proves no earlier event.
- **Provenance limit:** Captured execution comments are owner-attested. Their digests bind the report to the preserved command and output, but they are not cryptographic signatures from Codex or Cubic. Do not claim that a free-form execution identifier authenticates a reviewer or that a later export proves the original existed before merge.
- **Prospective root:** Admit only the exact corrected PR merge commit after separate non-authoring full-baseline review, direct ChatGPT inspection of source and tests, applicable successful CI, and owner `admit-baseline` authorization. The owner admission and readiness index must precede the original release dispatch. The first release source and builder equal this commit; policy identity is derived separately. No ordinary integration may follow the root before dispatch. All later integrations require ordinary evidence and Git coverage.
- **Rejected alternatives:** Repin `BOOTSTRAP_BASELINE`, use a one-SHA exception, fabricate ordinary records, infer chronology from a late summary, treat tree equality as ancestry, rewrite old PR evidence, or allow a rerun to repair a late owner admission.
- **Invariants:** Keep schema-v1 verification for already frozen signed releases while refusing schema-v1 new admission. Preserve exact source/policy/builder identities, first-parent coverage, immutable release verification and attestations, deterministic eight-asset packaging, historical task pins and compatibility-sensitive markers. Fail closed on missing or contradictory timestamps, edited original records, wrong PR/CI identities, unresolved material findings, late admission and any changed baseline tree.
- **Read-only audit:** Use one explicitly selected read-only GitHub credential, verify it authenticates as `danielbyon`, and refuse every write. Report `PASS`, `FAIL`, `MISSING_EVIDENCE` and `NOT_RUN` by gate. The audit may qualify ordinary pre-merge evidence or prospective pre-dispatch admission, but it never dispatches the release workflow.
- **Exclusions:** Actual baseline admission, implementation merge, production workflow dispatch, release publication, credential configuration, Skill installation, task-pin migration and MCP lifecycle remain separate owner-authorized work. Issue #22 continues to own release deployment and activation qualification.
